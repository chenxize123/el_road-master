# 课程视频顺序与删除接口（后端契约提案）

## 1. 背景与范围

当前前端使用以下接口获取课程视频、播放视频和上传视频：

- `GET /course/video/course_id?course_id={course_id}`：获取视频列表
- `GET /file/course/video?object_name={object_name}&expires={seconds}`：获取临时播放地址
- `POST /course/video/`：上传视频

现有接口没有持久化修改视频顺序或删除视频的能力。本提案增加排序和删除接口，让管理员、教师的操作写入数据库并在刷新及其他客户端生效。**以下接口是待后端实现的契约，不代表当前服务已经提供。**

基础地址为 `{API_BASE_URL}`。所有接口沿用项目现有 JSON 响应格式：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

请求需要携带登录令牌：

```http
Authorization: Bearer <token>
Content-Type: application/json
```

## 2. 视频列表返回顺序字段

现有列表接口继续使用：

```http
GET /course/video/course_id?course_id={course_id}
```

后端应按 `sort_order` 升序返回视频；排序值相同的记录以 `id` 升序作为稳定的兜底排序。建议每条视频记录返回 `sort_order`：

```json
{
  "code": 200,
  "message": "success",
  "data": [
    {
      "id": "9007199254740993",
      "course_id": "123",
      "title": "第1章 - 自然语言处理概述",
      "video": "course/123/chapter-1.mp4",
      "sort_order": 0
    },
    {
      "id": "9007199254740994",
      "course_id": "123",
      "title": "第2章 - 自然语言处理编程基础",
      "video": "course/123/chapter-2.mp4",
      "sort_order": 1
    }
  ]
}
```

ID 可能是大整数。客户端应将 ID 当作字符串处理；后端应接受并返回能无损表示的 ID。

## 3. 保存视频顺序

### 请求

```http
PUT /course/video/order/
```

```json
{
  "course_id": "123",
  "video_ids": [
    "9007199254740994",
    "9007199254740993",
    "9007199254740995"
  ]
}
```

`video_ids` 表示该课程当前全部未删除视频的完整目标顺序，数组第一个视频排在最前。使用视频 ID 而不是文件路径，避免客户端伪造或替换对象存储路径。

### 成功响应

```json
{
  "code": 200,
  "message": "视频顺序已保存",
  "data": {
    "course_id": "123",
    "video_ids": [
      "9007199254740994",
      "9007199254740993",
      "9007199254740995"
    ]
  }
}
```

### 后端处理要求

1. 验证当前用户已登录，且为管理员或该课程的任课教师/所有者。不能只信任前端隐藏按钮。
2. 验证课程存在且当前用户有权管理该课程。
3. 验证 `video_ids` 是数组、无重复，且与该课程当前全部未删除视频 ID 完全匹配。拒绝跨课程 ID、缺失 ID、多余 ID 和重复 ID。
4. 在一个数据库事务中更新所有视频的顺序，建议写入连续值 `0..N-1`；任何一条更新失败时全部回滚，避免出现半完成排序。
5. 空列表可以是合法输入（用于课程下无视频的场景）；课程有视频时，空列表应因未包含全部视频而校验失败。
6. 同一课程的并发排序请求应串行化或检测版本冲突，避免请求互相覆盖且客户端无法判断最终顺序。若采用版本检测，可在列表响应中加入 `order_version`，并要求请求携带该版本。
7. 再次调用相同顺序应安全，得到相同结果。

### 建议错误响应

```json
{
  "code": 400,
  "message": "video_ids 必须包含该课程全部未删除视频且不能重复",
  "data": null
}
```

## 4. 删除课程视频

### 请求

```http
DELETE /course/video/?video_id=9007199254740993
```

请求中只传视频记录 ID。后端必须从数据库记录中取得课程 ID 和对象存储路径；不可直接信任客户端传入的 `object_name`。

### 成功响应

```json
{
  "code": 200,
  "message": "视频已删除",
  "data": {
    "id": "9007199254740993",
    "deleted": true
  }
}
```

### 后端处理要求

1. 验证当前用户已登录，且为管理员或该视频所属课程的任课教师/所有者。
2. 通过 `video_id` 查询数据库记录，并确认其所属课程和存储对象。
3. 删除该视频的数据库记录及对应存储对象，使其不再出现在列表中、不能再通过应用获取播放地址。
4. 处理数据库与对象存储无法共享事务的问题：推荐先标记记录为待删除/已删除，再删除对象，成功后完成记录清理；存储删除失败时保留可重试状态并返回失败，不能返回成功但遗留孤立文件。
5. 对已删除或不存在的视频返回 `404`，不应删除其他课程的数据。若实现幂等删除并对重复请求返回成功，应在后端统一约定并保持一致。
6. 若删除会影响已有学习记录或审计要求，可采用软删除并禁止列表及播放接口返回该视频；相关业务保留策略由后端确定。
7. 删除后重新获取列表，`sort_order` 应保持连续或至少仍能按升序稳定展示。

## 5. 错误状态与权限

建议 HTTP 状态码与响应 `code` 一致：

| HTTP 状态 | 场景 |
| --- | --- |
| `400` | 参数格式错误、视频 ID 重复、排序列表与课程视频集合不一致 |
| `401` | 未登录或令牌无效 |
| `403` | 已登录，但不是管理员或有权管理该课程的教师 |
| `404` | 课程或视频不存在 |
| `409` | 排序版本冲突（仅在启用版本检查时） |
| `500` | 数据库或存储操作失败；响应中不得伪报成功 |

示例：

```json
{
  "code": 403,
  "message": "无权管理该课程的视频",
  "data": null
}
```

## 6. 数据库建议

在视频表中新增：

```text
sort_order INTEGER NOT NULL DEFAULT 0
```

建议为 `(course_id, sort_order, id)` 建立索引。迁移已有数据时，应为每门课程按当前列表顺序分配 `0..N-1`，避免所有旧视频使用相同默认值而导致排序不稳定。

## 7. 前端接入与验收

后端部署后，前端应将当前页面的临时上移/下移操作改为调用排序接口，并在失败时恢复列表顺序、提示失败原因；删除操作应调用删除接口，成功后刷新列表并切换当前播放项。

验收至少覆盖：

1. 管理员和有权教师可以调整顺序、删除视频；普通学生不能调用管理接口。
2. 调整顺序后刷新页面，列表顺序保持不变。
3. 其他用户重新加载列表后看到相同顺序。
4. 删除成功后刷新列表，视频不再出现，播放链接不再可用，存储对象按策略完成清理。
5. 未授权、跨课程 ID、重复 ID、遗漏视频、数据库失败及对象存储失败均返回明确错误，且不会产生部分排序或伪成功。
